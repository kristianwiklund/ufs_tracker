# Creating a Release

This guide explains how to create a new release of UFS Maritime Notices Tracker.

## Quick Start

### Option 1: Manual Release Workflow (Recommended)

The easiest way to create a release is using the manual workflow:

1. Go to your GitHub repository
2. Click on **Actions** tab
3. Click on **Create Release** workflow (left sidebar)
4. Click **Run workflow** button (right side)
5. Fill in the form:
   - **Version number**: e.g., `v1.0.0` (must start with 'v')
   - **Mark as pre-release**: Check if this is a beta/test release
6. Click **Run workflow**

The workflow will:
- ✅ Validate the version format
- ✅ Create and push a git tag
- ✅ Build Windows executables (both Desktop and Console versions)
- ✅ Create a ZIP package
- ✅ Publish a GitHub Release with download links
- ✅ Generate release notes automatically

### Option 2: Automatic Release on Tag Push

You can also trigger a release by pushing a version tag:

```bash
# Create a new version tag
git tag v1.0.0

# Push the tag to GitHub
git push origin v1.0.0
```

This will trigger the build workflows, which will automatically create a release.

## Version Numbering

Follow [Semantic Versioning](https://semver.org/):

- **Format**: `vMAJOR.MINOR.PATCH`
- **Example**: `v1.2.3`

**When to increment**:
- **MAJOR** (v2.0.0): Breaking changes, major redesign
- **MINOR** (v1.1.0): New features, backwards compatible
- **PATCH** (v1.0.1): Bug fixes, small improvements

**Examples**:
- First release: `v1.0.0`
- Added new feature: `v1.1.0`
- Fixed a bug: `v1.0.1`
- Beta testing: `v1.0.0-beta` (mark as pre-release)

## Release Checklist

Before creating a release:

- [ ] All tests pass
- [ ] Documentation is up to date
- [ ] CHANGELOG.md is updated (if you have one)
- [ ] Version number is decided
- [ ] Built and tested locally

## After Release is Published

### Verify the Release

1. Go to the [Releases page](https://github.com/kristianwiklund/ufs_tracker/releases)
2. Find your new release
3. Download the Windows package
4. Extract and test both versions:
   - Desktop app: Run `start.bat`
   - Console app: Run `start-console.bat`

### Announce the Release

Consider announcing on:
- GitHub Discussions (if enabled)
- Project README.md (add a "Latest Release" badge)
- Social media or relevant forums

### If Something Goes Wrong

**Delete the Release**:
1. Go to Releases page
2. Click on the release
3. Click **Delete** button
4. Confirm deletion

**Delete the Tag**:
```bash
# Delete local tag
git tag -d v1.0.0

# Delete remote tag
git push origin :refs/tags/v1.0.0
```

Then fix the issue and create a new release with the next version number.

## Automation Details

### Build Process

The release workflow performs these steps:

1. **Validation**: Checks version format (must be `vX.X.X`)
2. **Tagging**: Creates and pushes git tag
3. **Windows Build**:
   - Sets up Python 3.11
   - Installs dependencies
   - Builds Desktop executable with PyInstaller
   - Builds Console executable with PyInstaller
   - Creates portable package
   - Compresses to ZIP
4. **Release Creation**:
   - Generates release notes
   - Creates GitHub Release
   - Uploads Windows ZIP
   - Sets pre-release flag if specified

### Build Time

Expected workflow duration:
- Windows build: ~5-10 minutes
- Total: ~10-15 minutes

## Troubleshooting

### "Tag already exists" Error

**Cause**: You're trying to create a tag that already exists.

**Solution**: Choose a different version number or delete the existing tag first.

### "Version must be in format v1.0.0" Error

**Cause**: Version number doesn't match the required format.

**Solution**: Use format `vX.X.X` (e.g., `v1.2.3`). The 'v' prefix is required.

### Build Fails

**Check**:
1. Go to Actions tab
2. Click on the failed workflow run
3. Expand the failed step to see error details
4. Common issues:
   - Missing dependencies in requirements.txt
   - PyInstaller can't find templates folder
   - Import errors (add to hidden-imports)

### ZIP is Empty or Corrupted

**Cause**: Build step failed silently.

**Solution**: Check workflow logs, specifically the "Build Desktop GUI executable" and "Create portable package" steps.

## Advanced: Customizing Release Notes

The workflow auto-generates release notes. To customize:

1. Edit `.github/workflows/release.yml`
2. Find the "Generate release notes" step
3. Modify the `release_notes.md` content
4. Commit and push changes
